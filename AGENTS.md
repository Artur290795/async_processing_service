# Инструкции для агентов

## Контекст проекта

Это тестовое задание: асинхронный сервис обработки платежей на FastAPI, PostgreSQL, RabbitMQ/FastStream, SQLAlchemy 2.0 и Alembic. Подробный план реализации находится в [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md); перед началом существенной работы прочитайте его полностью.

## Цель

Сервис принимает платежи по HTTP, создаёт платёж и событие outbox в одной транзакции, публикует событие в RabbitMQ, обрабатывает его асинхронно и уведомляет клиента webhook-ом.

## Обязательные инварианты

- Используйте Python async-подход во всём пути работы с БД, брокером и HTTP-клиентом.
- `POST /api/v1/payments` требует `X-API-Key` и `Idempotency-Key`, возвращает `202 Accepted`.
- Повторный запрос с тем же `Idempotency-Key` не создаёт второй платёж или второе outbox-событие.
- Создание `Payment` и `OutboxEvent` всегда происходит в одной транзакции БД.
- API не публикует задачу напрямую в RabbitMQ. Сначала outbox, затем отдельный publisher.
- Доставка сообщения at-least-once: consumer обязан быть идемпотентным и не менять уже финальный (`succeeded`/`failed`) платёж.
- Для проблемных сообщений нужны ровно до трёх попыток с экспоненциальной задержкой и DLQ.
- Webhook считается успешным только при HTTP 2xx; ошибки сети, таймауты и не-2xx должны попадать в retry-логику.
- Денежные суммы храните и передавайте как `Decimal`/`NUMERIC`, никогда не как `float`.
- Все секреты и DSN задаются переменными окружения. Не добавляйте реальные ключи или `.env` в Git.

## Предпочтительная структура

```text
app/
  api/          # routes и FastAPI dependencies
  broker/       # topology, FastStream handlers, publisher
  core/         # settings, auth, logging
  db/           # async engine, session, metadata
  models/       # SQLAlchemy ORM
  repositories/ # доступ к БД
  schemas/      # Pydantic request/response models
  services/     # бизнес-логика, webhook, gateway
  main.py       # API
  consumer.py   # worker
alembic/
tests/
```

Не помещайте SQL или бизнес-логику в роуты. Внешний платёжный шлюз, генератор исхода 90/10, clock и ожидания должны быть изолированы за интерфейсами, чтобы тесты не зависели от случайности и реального времени.

## Качество и проверка

Перед завершением изменения:

1. Добавьте или обновите тесты, если поведение изменилось.
2. Запустите форматирование/линтер и релевантные тесты.
3. Если затронуты миграции, проверьте применение на чистой базе.
4. Если затронуты Docker или брокер, выполните smoke-test через Docker Compose или явно сообщите, почему это невозможно.
5. Обновите README, если изменились запуск, переменные окружения, API или операционное поведение.

## Ограничения изменений

- Не ослабляйте уникальность `idempotency_key`, transactional outbox, auth, retry или DLQ ради упрощения.
- Не делайте необратимых изменений схемы без миграции Alembic.
- Не добавляйте синхронные драйверы, блокирующие `sleep` или сетевые вызовы в async-код.
- Не помечайте outbox-событие опубликованным до подтверждённой публикации брокером.
- При неясности поведения выберите безопасный вариант, зафиксируйте допущение в README и покройте его тестом.
