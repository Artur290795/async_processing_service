# План реализации: асинхронный сервис обработки платежей

## Цель

Реализовать запускаемый через Docker Compose микросервис, который принимает платежи по HTTP, надёжно публикует задания в RabbitMQ через transactional outbox, асинхронно обрабатывает их и уведомляет клиента через webhook.

## Обязательный результат

- FastAPI API с `POST /api/v1/payments` и `GET /api/v1/payments/{payment_id}`.
- PostgreSQL, асинхронный SQLAlchemy 2.0 и Alembic-миграции.
- RabbitMQ и один consumer на FastStream.
- Transactional outbox: запись платежа и события в outbox происходят в одной транзакции; отдельный publisher доставляет событие в RabbitMQ и отмечает запись опубликованной только после подтверждённой публикации.
- Идемпотентность по обязательному заголовку `Idempotency-Key`.
- Обработка платежа с задержкой 2-5 секунд и результатом: 90% `succeeded`, 10% `failed`.
- Отправка webhook с тремя попытками и экспоненциальной задержкой; окончательно неудавшиеся сообщения попадают в DLQ.
- `docker-compose.yml` с PostgreSQL, RabbitMQ, API и consumer (outbox publisher может работать внутри consumer либо отдельным сервисом, но это должно быть явно описано).
- README с полной инструкцией запуска, переменными окружения, curl-примерами и способом проверить очереди/DLQ.

## Архитектурные решения

1. **Слои.** Разделить HTTP-маршруты, Pydantic-схемы, ORM-модели, репозитории/сервисы, брокер и фоновые задачи. Маршруты не должны содержать бизнес-логику или SQL.
2. **Транзакция создания платежа.** В одной транзакции PostgreSQL:
   - найти платёж по `idempotency_key`;
   - если ключ уже существует, вернуть сохранённый платёж без новой outbox-записи;
   - иначе создать `Payment(status=pending)` и `OutboxEvent(event_type="payment.created", payload=...)`.
3. **Outbox publisher.** Периодически выбирать неопубликованные outbox-записи с блокировкой `FOR UPDATE SKIP LOCKED`, публиковать payload в `payments.new`, затем в отдельной короткой транзакции записывать `published_at`. При ошибке оставлять запись доступной для повторной публикации. Consumer обязан быть идемпотентным, потому что доставка всё равно at-least-once.
4. **Брокер.** Настроить durable-очередь `payments.new`, DLX и durable DLQ (например, `payments.dlq`). Для retry использовать либо TTL retry-очереди с dead-letter обратно в рабочую очередь, либо встроенную стратегию повторов FastStream; выбранный способ должен давать ровно максимум три обработки и экспоненциальную задержку.
5. **Consumer.** Для каждого сообщения атомарно получить платёж, пропустить его, если он уже финальный, иначе эмулировать шлюз, установить финальный статус и `processed_at`. Лишь после фиксации статуса вызывать webhook. Сообщение подтверждать только после успешной обработки; при исчерпании попыток направлять в DLQ.
6. **Webhook.** Отправлять JSON с идентификатором, суммой, валютой, итоговым статусом и временем обработки. При не-2xx, таймауте или сетевой ошибке считать доставку неуспешной. Логировать номер попытки и причину ошибки, не раскрывая секреты.
7. **Конфигурация и безопасность.** Хранить `API_KEY`, DSN PostgreSQL, URL RabbitMQ, настройки retry и таймаут webhook в переменных окружения. Проверять `X-API-Key` до выполнения всех endpoint'ов. Не добавлять реальные ключи в репозиторий; подготовить `.env.example`.

## План работ

### 1. Каркас и локальная инфраструктура

- Создать pyproject/requirements с совместимыми версиями FastAPI, Pydantic v2, SQLAlchemy 2.x, asyncpg, Alembic, FastStream RabbitMQ, HTTP-клиента и тестовых библиотек.
- Настроить settings через Pydantic Settings и `.env.example`.
- Добавить Dockerfile и Compose со healthcheck для PostgreSQL и RabbitMQ; API/consumer должны ждать готовность зависимостей.
- Настроить структурированное логирование и уникальный correlation/payment ID в сообщениях, где это уместно.

### 2. База данных и миграции

- Описать таблицу `payments`: UUID/строковый `id`, `amount` как `NUMERIC`, `currency`, `description`, JSONB `metadata`, `status`, уникальный `idempotency_key`, `webhook_url`, `created_at`, `processed_at`, при необходимости `updated_at`.
- Описать таблицу `outbox`: ID, `aggregate_id/payment_id`, `event_type`, JSONB payload, `created_at`, `published_at`, счётчик/диагностика попыток.
- Создать начальную Alembic-миграцию с индексами: уникальный индекс на `idempotency_key`, индекс по неопубликованным outbox-событиям.
- Проверить, что миграции выполняются на чистой БД в контейнере.

### 3. HTTP API

- Реализовать схему входных данных: положительная сумма с Decimal, валюта из `RUB/USD/EUR`, непустое описание (если принято как обязательное), JSON metadata и валидный HTTP(S) `webhook_url`.
- Реализовать dependency для `X-API-Key`: отсутствие/неверное значение -> `401` или `403`, выбранный контракт задокументировать.
- Реализовать `POST /api/v1/payments`: обязательный `Idempotency-Key`, атомарное создание платежа + outbox-события, `202 Accepted`, поля `payment_id`, `status`, `created_at`.
- Определить поведение при повторном ключе с иным body: предпочтительно возвращать исходный результат и явно описать это в README; альтернативно `409 Conflict`, но правило должно быть стабильным и покрытым тестом.
- Реализовать `GET /api/v1/payments/{payment_id}`: полный DTO, `404` для неизвестного ID.
- Добавить единый формат ошибок и OpenAPI-примеры.

### 4. Outbox и RabbitMQ

- Объявить exchange, основную очередь `payments.new`, retry-механику и DLQ декларативно при запуске.
- Реализовать publisher с безопасной конкурентной выборкой outbox-записей и обработкой сбоя публикации.
- Сериализовать event payload с `payment_id` и версией события; consumer не должен зависеть от неявного состояния в памяти API.
- Подтвердить, что API не публикует напрямую в RabbitMQ: именно это сохраняет событие при падении брокера после HTTP-запроса.

### 5. Обработка платежа и webhook

- Consumer получает `payment_id`, загружает запись и делает обработку идемпотентной.
- Задержку 2-5 секунд и вероятность 90/10 вынести в отдельный gateway-адаптер, чтобы их можно было стабильно подменять в тестах.
- Сохранять итоговый статус перед webhook; повторная доставка сообщения не должна снова менять уже финальный платёж.
- Реализовать HTTP-клиент с ограничением времени ожидания и retry (до трёх попыток с экспоненциальной задержкой).
- В случае окончательной неудачи передать сообщение в DLQ вместе с причиной и числом попыток. Сохранить диагностический лог; опционально вести отдельные поля доставки webhook, если это не расширяет задание чрезмерно.

### 6. Тесты

- Unit: валидация схем, API-key, создание платежа, получение платежа, неизвестный ID.
- Unit/интеграционные: повтор того же `Idempotency-Key` не создаёт второй платёж и второе событие outbox.
- Интеграционные: в одной транзакции создаются payment + outbox; publisher помечает запись опубликованной только после успешной публикации.
- Consumer: успех, ошибка шлюза, повторная доставка финального платежа, три неудачи webhook и маршрутизация в DLQ.
- Docker smoke-test: миграции, POST, polling GET до финального статуса и получение webhook тестовым HTTP-сервером.
- Не использовать случайность и реальные `sleep` в unit-тестах: gateway, clock и задержки должны быть подменяемыми.

### 7. Документация и финальная проверка

- README: архитектурная схема, объяснение гарантий (at-least-once, почему consumer идемпотентен), быстрый старт, конфигурация, миграции, curl-примеры, проверка RabbitMQ Management UI и DLQ.
- Указать известную семантику: webhook может быть доставлен более одного раза при сбое после отправки; получатель должен принимать идентификатор платежа как ключ идемпотентности.
- Выполнить форматирование, линтер, тесты и `docker compose up --build`; вручную проверить основной сценарий и сценарий сбоя.

## Критерии приёмки

- Повторный POST с тем же `Idempotency-Key` не создаёт дополнительных строк в `payments` и `outbox`.
- Платёж, принятый API при временно недоступном RabbitMQ, остаётся в БД и будет опубликован после восстановления broker'а.
- Очередь, retry и DLQ созданы как durable; сообщение не теряется при перезапуске сервисов.
- Платёж заканчивается в `succeeded` или `failed`, а GET возвращает актуальное состояние.
- Webhook получает ожидаемый payload; при трёх сбоях сообщение доступно для анализа в DLQ.
- Чистый клон запускается по README без ручной настройки, кроме копирования `.env.example` в `.env` и задания безопасного `API_KEY`.

## Неопределённости, которые следует зафиксировать перед реализацией

- Что считать идентичным повторным запросом: ключ сам по себе или ключ + fingerprint body.
- Должен ли платеж со статусом `failed` обрабатываться повторно вручную, и нужен ли для этого endpoint.
- Нужна ли строгая гарантия доставки webhook; базовое задание требует retries/DLQ, но не требует отдельной webhook-outbox таблицы.
- Допустим ли встроенный polling outbox publisher или нужен отдельный сервис в Compose. Рекомендуется отдельный процесс/сервис, чтобы API оставался stateless.
